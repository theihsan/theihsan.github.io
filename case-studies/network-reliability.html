Multi-Site Network Reliability

Ultraction General Contracting LLC · Abu Dhabi, UAE · Network & Remote Access
01 — Context & Problem
A remote-access path that looked healthy wasn't

A mesh-style remote-access layer is used across the organization's multi-site network to let authorized devices reach shared file storage between offices. This access path began silently failing — the affected devices showed a normal "Connected" state, with no error, no alert, and no obvious symptom pointing to the cause.

Separately, the same period involved consolidating a fragmented Wi-Fi SSID setup that had grown inconsistently across sites, which is covered under Implementation below.

02 — Environment
Multi-site network, sole ownership

Multi-site MikroTik-based network infrastructure across 3+ locations, with a mesh VPN layer used specifically for inter-office file sharing. All network and remote-access configuration is owned solely, with no dedicated network team or second-line escalation.

03 — My Responsibility
Full ownership of network and remote-access configuration

As the sole owner of this infrastructure, diagnosing and resolving the fault — end to end, from initial report through root cause to validated fix — was entirely my responsibility. There was no network team to hand this off to.

04 — Investigation
Ruling out the obvious explanation first

The mesh dashboard showed every affected peer as Connected — the standard first thing to check when remote access fails, and it gave no indication of a problem. Because the fault affected multiple, unrelated devices identically, client-side configuration was ruled out early: a per-device issue doesn't produce an identical symptom across an entire device set. That pointed the investigation toward something shared — a policy or network-level cause rather than an endpoint problem.

05 — Root Cause
A connected state with an empty access policy

The mesh network's access-control policy file had an empty grants array. With no explicit grants defined, the policy engine defaulted to deny-all — meaning every peer could establish a connection at the transport level (hence "Connected") while being denied at the authorization level. The connection status and the authorization state were two separate things, and only one of them was visible on the dashboard.

07 — Implementation
Restoring the correct grant, then addressing the wider Wi-Fi layout
  • Restored the correct access grant in the mesh policy configuration, re-establishing the intended traffic path between authorized peers.
  • Separately, consolidated a fragmented Wi-Fi SSID structure that had accumulated inconsistently across multiple sites into a single, simplified structure, and resolved DFS channel conflicts that were affecting coverage.
08 — Security Considerations
Restoring access deliberately, not broadly

The fix was scoped to restore exactly the access that was intended — not to open broader permissions as a shortcut. This incident is also a useful reminder in itself: a "Connected" status is not proof of authorized access, and access-control policy needs to be checked independently of connection state during any similar investigation going forward.

09 — Validation
Confirmed at the traffic level, not the status level

Given that the original symptom was a healthy-looking status hiding a real fault, validation didn't stop at checking the dashboard again — it required confirming actual file-sharing traffic flowed correctly between the previously affected peers post-fix, with access scoped to exactly what was restored.

10 — Result
Access restored, coverage simplified

Remote file-sharing access was restored without extended downtime for the affected offices. The Wi-Fi SSID consolidation that followed improved coverage consistency across sites by removing the channel conflicts and structural sprawl that had built up over time.
